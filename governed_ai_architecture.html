Governed AI
Execution System

A six-layer architecture where the LLM is not the controller — it is the bounded executor inside a governed system. Every request passes through classification, policy, and human approval before any model acts.

Status Architecture Complete

01 · Philosophy

Core Principle

Most AI products treat the LLM as the orchestrator and bolt governance on as an afterthought. This system inverts that. Governance is the product. The LLM is the last mile.

"The LLM is not the controller. The LLM is the bounded executor inside a governed system."

— Core architectural principle

Every request travels through six layers before any model acts. Classification happens before execution. Policy is applied before dispatch. A human approves before anything changes. The audit record exists before the result is returned.

This matters most in regulated industries — finance, healthcare, legal, defense — where that distinction between "AI that decides" and "AI that executes under control" is the difference between adoption and rejection.

03 · Layer Details

Layer Specifications

Layer 1

Product UI

The only surface the user directly touches. Everything else is invisible from here.
Create project Connect repo Define vision Define schema API contract Security rules Policy profile Submit requests Review approvals Review WPs Review reports Review validations
This layer is just the user-facing surface. It does not execute, classify, or decide. It captures intent and displays results.
Layer 2

Platform / Project State

The backend application. Keeps the product itself working.
Users Projects Repo connections Stored UI forms Auth API tokens Project metadata UI↔repo sync
Manages state only. Does not classify requests. Does not execute anything. Passes validated requests to Layer 3.
Layer 3

Interpretation / Control

agent_control_stack. The gatekeeper. No execution happens without passing through here.
Restore context Balance / normalize Classify Apply policy Apply approvals

Decision outcomes

DecisionMeaning
clarifyRequest is ambiguous — return to user for more information
refuseRequest violates policy — terminated immediately
dispatchRequest is approved — forward to HITL gate then Layer 4
escalateRequest exceeds current authority — routed to higher review
The LLM moat lives here. This layer is the hardest to replicate and the most valuable to compliance-heavy buyers.
Layer 4

Governed Execution (AOS / CDD)

Decides exactly how execution is bounded. Only reached after HITL approval.
Choose artifact path Load constraints Load WP Load session Check vault health Change-control routing Dry-run flag
This layer never executes. It only decides how execution will be bounded, then hands off to Layer 5.
Layer 5

Agent / Tool Execution

Only here does the LLM or tool actually act. The model is the last step, not the first.
Implement code Draft artifacts Review outputs Run validation commands Produce completion evidence
All prior layers have already allowed this. The model executes within bounds that were fully defined before it was invoked.
Layer 6

Audit / Ops

Everything gets recorded. Provides visibility, control, and the data source for policy refinement.
Request Decision Traces Policy context Approvals Execution results Reports Retention CI validation
Audit is a first-class layer, not an afterthought. It feeds the policy feedback loop and surfaces results back to the UI.
04 · V1 Constraint

Single Request Lock

For the test phase, concurrency is solved with a simple lock. One active request per project at a time. This eliminates queue management, priority lanes, and partial execution recovery as v1 concerns.

Lock mechanism

is_processing: false ← project is available Submit request ↓ is_processing → true ← UI disables submit button ↓ Request travels through all 6 layers ↓ Execution completes (success or failure) ↓ is_processing → false ← project is available again

The only edge case to handle is a stuck lock. If is_processing remains true beyond a defined timeout, auto-release and mark the request as FAILED. A manual force-unlock button in the UI is sufficient for v1.

When ready to scale: replace the boolean lock with a job queue. The architecture does not change — only the concurrency mechanism does.

05 · Gap Components

V1 Gap Specifications

Four components complete the architecture. Each is defined below with behavior, state flow, and explicit non-goals. Non-goals are as binding as goals.

01

HITL Gate — Human-in-the-Loop

Controlled approval checkpoint between classification and execution
Trigger

Every request Layer 3 classifies as DISPATCH enters this gate. Requests classified as REFUSE or CLARIFY never reach it.

State machine
SUBMITTED → CLASSIFIED → PENDING_APPROVAL → APPROVED → DISPATCHED ↓ REJECTED → TERMINATED ↓ ESCALATED → PENDING_REVIEW
Stored at PENDING_APPROVAL
FieldPurpose
request_textOriginal request exactly as submitted
policy_decisionClassification and risk level from Layer 3
intended_actionsWhat Layer 4 would execute if approved
project_contextRequesting user, project, timestamp
expires_atAuto-expire TTL — prevents stuck pending states
Human choices
ChoiceOutcome
ApproveRequest dispatched to Layer 4
RejectRequest terminated, user notified with reason
EscalateMoved to PENDING_REVIEW, assigned to higher authority
Key principle This is a state machine + DB record + UI screen. It is not an AI problem. No model makes or influences this decision.
Non-goals (v1)
No auto-approval based on risk score
No approval delegation or routing rules
No SLA enforcement or escalation timers
02

Rollback Path — Failure Handling

Structured, observable failure response — not automatic recovery
Failure flow
EXECUTION_FAILED ↓ Capture error + full execution trace ↓ Set request status → FAILED ↓ Store all artifacts produced up to failure point ↓ Notify user via UI with plain-language summary ↓ Lock released → project available for next request
Stored on failure

ElementDescription

Key principle Start with observability and clarity, not automatic recovery. A human reading a failure trace and deciding what to do next is the correct v1 behavior.
Non-goals (v1)
No automatic repo revert
No artifact undo or rollback
No retry logic or auto-recovery
No compensation transactions
03

Dry-Run Mode

Full logic execution without committing any side effects
How it is invoked

User selects dry-run in the UI before submitting. Layer 4 receives the flag mode = DRY_RUN which propagates through the entire execution chain.

The contract — inverted by design
Tool receives request ↓ Execute full logic ↓ Generate outputs and completion evidence ↓ Check: mode == DRY_RUN? YES → skip all write operations, log "would have written X" NO → execute writes normally

Tools are read-only by default. A tool must explicitly declare write capability to perform side effects. If a new tool is added and the developer forgets to handle the dry-run flag, the tool does nothing — it fails safely rather than causing unintended writes.

What dry-run produces
OutputDescription
Execution traceEvery step that would have run
Skipped writes logList of writes that were bypassed
Draft artifactsOutputs in draft state, not committed
Validation resultsChecks that would have passed or failed
Summary"X would have changed, Y would have been created"
Key principle Dry-run is not a feature — it is a discipline enforced across the system. Every tool author declares write capability. The system enforces the contract.
Non-goals (v1)
No partial dry-run — either the full request is dry or it is not
No comparison diff between dry-run and live execution
No automatic promotion from dry-run to live
04

Policy Feedback Loop

Human-driven policy refinement based on real execution data
Data surfaced by Layer 6
DataPurpose
Execution resultsSee what succeeded and what failed
Policy violationsSee which rules triggered and how often
HITL decisionsSee what humans approved, rejected, escalated
Decision tracesSee exactly why Layer 3 classified each request
Failure tracesSee where execution broke down
The feedback cycle
Execution happens ↓ Layer 6 records everything ↓ Human reviews dashboard ↓ Human identifies gaps: wrong classification / over-blocking / under-blocking ↓ Human manually updates policy profiles in UI ↓ Policy version saved: author + timestamp + reason (required) ↓ Policy committed to repo as artifact (same change-control as code) ↓ New policy applies to all subsequent requests
Policy versioning

Every policy change is stored as a versioned record. Policy profiles are also committed to the repo as artifacts, meaning they go through the same change-control as code.

FieldDescription
previous_stateFull snapshot of policy before the change
new_stateFull snapshot of policy after the change
changed_byUser who made the change
changed_atTimestamp of the change
reasonFree text explanation — required, cannot be left blank
Key principle Policy evolves through human judgment, not autonomous adaptation. The dashboard is a tool for informed human decision-making, not a suggestion engine.
Non-goals (v1)
No automatic policy mutation based on patterns
No self-learning or model-driven policy updates
No A/B testing of policy variants
No policy recommendations from the system
